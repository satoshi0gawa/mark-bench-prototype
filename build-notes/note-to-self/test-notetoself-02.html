公開URLが404になる、変更が反映されない、CSSや画像だけ読み込まれない場合に、原因を混ぜずに切り分けられるよう確認順を整理する。

01 / OVERVIEW

確認する順番を決める

GitHub Pagesが表示されないときは、設定を同時に変更せず、公開処理、公開物、URL、ブラウザ表示の順に確認する。原因を切り分ける前に複数箇所を直すと、どの変更で解消したか分からなくなる。

02 / STATUS

GitHub側の状態を確認する

最初にGitHub StatusでPagesやActionsに障害が発生していないかを確認する。サービス側の問題であれば、リポジトリ設定を変更しても解消しない。

次にリポジトリのActionsを開き、最新のデプロイが成功しているかを見る。失敗している場合は、失敗したジョブとステップを特定し、最初に表示されたエラーから確認する。

  1. 最新コミットがGitHubへプッシュされているか確認する。
  2. そのコミットを起点とするワークフローがあるか確認する。
  3. ビルドとデプロイの両方が成功しているか確認する。
  4. Pages設定に表示される公開URLを開く。

03 / SOURCE

公開元と成果物を確認する

ブランチから公開している場合は、SettingsのPagesで選択したブランチとフォルダーを確認する。/docsを指定しているのにフォルダーが存在しない場合や、別ブランチへだけ変更を反映した場合は公開されない。

GitHub Actionsから公開している場合は、デプロイ対象のartifactへ必要なファイルが含まれているかを確認する。ソース側にindex.htmlがあっても、生成処理がartifactへ含めていなければ公開サイトからは参照できない。

source/
  index.html
  css/

dist/            <- deploy target
  index.html      <- required
  css/
BUILD OUTPUT

ソースディレクトリではなく、実際にデプロイされるフォルダーの中身を確認する。

04 / ENTRY FILE

入口ファイルを確認する

HTMLを入口にする場合、GitHub Pagesは公開元の最上位にあるindex.htmlを探す。ファイルが下位フォルダーだけにある場合や、公開元と異なる場所にある場合はトップページを表示できない。

ファイル名の大文字小文字も区別される。ローカル環境で表示できても、Index.html、index.HTML、参照先の文字ケース違いが公開環境で問題になる場合がある。

05 / PATHS

リンクとアセットパスを確認する

トップページは表示できるのにCSS、画像、下層リンクが404になる場合は、パスの基準を確認する。プロジェクトサイトの既定URLにはリポジトリ名が含まれるため、ドメイン直下を指すルート相対パスがリポジトリ配下を飛び越える場合がある。

root-relative path:     /css/style.css
document-relative path: ./css/style.css

project URL: https://<owner>.github.io/<repository>/

生成処理を使う場合は、開発サーバーだけでなく、GitHub Pagesと同じベースパスを想定した静的成果物でもリンクを確認する。ファイル名とHTML側の参照文字列は大文字小文字まで一致させる。

06 / DOMAIN

ドメインとキャッシュを確認する

独自ドメインを使用している場合は、まずPages設定に表示された既定のgithub.io URLで公開できているかを確認する。既定URLでも表示できなければ、DNSより前の公開設定や成果物に原因がある。

  1. Pages設定のCustom domainが意図した値か確認する。
  2. ドメイン事業者側のDNSレコードを確認する。
  3. リポジトリや成果物内のCNAMEを確認する。
  4. DNS反映を待ってからHTTPSの状態を確認する。
  5. シークレットウィンドウやキャッシュ削除後の表示を確認する。

問題が解消したら、一度に変更した設定を記録する。次回は同じ確認順を使い、サービス、公開処理、成果物、パス、ドメインのどこで止まっているかを先に特定する。
