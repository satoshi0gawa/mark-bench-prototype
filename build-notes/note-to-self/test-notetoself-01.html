01 / OVERVIEW

用語を役割ごとに分ける

GitHub Pagesは、リポジトリに置いた静的ファイルをWebサイトとして公開する仕組みである。設定画面にはリポジトリ、ブランチ、公開元、ビルド、デプロイなど複数の用語が並ぶが、それぞれが示す対象は異なる。

用語を覚えるときは、ファイルを保管する場所、公開対象を選ぶ設定、公開用ファイルを作る処理、完成物を配信する処理という役割に分けると整理しやすい。設定で迷った場合も、今確認しているのがどの役割かを先に判断する。

WORD MAP

Repository → Source → Build → Artifact → Deploy → Published site

02 / SITE TYPE

サイトの種類を区別する

GitHub Pagesには、ユーザーまたはOrganizationに対応するサイトと、個別のリポジトリに対応するプロジェクトサイトがある。種類によって既定URLとリポジトリ名の考え方が異なる。

GitHub Pagesのサイト種別と既定URL
種類リポジトリ既定URL
ユーザーサイト<owner>.github.iohttps://<owner>.github.io/
Organizationサイト<organization>.github.iohttps://<organization>.github.io/
プロジェクトサイト対象プロジェクトのリポジトリhttps://<owner>.github.io/<repository>/

プロジェクトサイトではURLにリポジトリ名が含まれるため、ルート相対パスを使うと参照先が想定とずれる場合がある。サイト種別はURL設計とアセットパスを確認するときの前提になる。

03 / REPOSITORY

リポジトリとブランチを確認する

リポジトリはサイトのソースや設定を保管する単位である。ブランチは同じリポジトリ内で作業履歴を分ける仕組みであり、Pagesの公開元として特定のブランチを選ぶ場合がある。

既定ブランチと公開ブランチは必ずしも同じではない。設定を確認するときは、編集したファイルがどのブランチへコミットされ、そのブランチが公開対象になっているかを分けて見る。

repository: example-site
default branch: main
publishing branch: main
publishing folder: /(root)
CHECK POINT

ローカルで編集しているブランチ、GitHubへプッシュしたブランチ、Pagesが参照するブランチの3つを一致させて確認する。

04 / SOURCE

公開元の違いを理解する

公開元は、GitHub Pagesが公開用ファイルをどこから受け取るかを示す。ブランチから公開する方法では、対象ブランチのルートまたは/docsを選ぶ。GitHub Actionsを使う方法では、ワークフローが生成した成果物を公開する。

公開元の方式と確認場所
方式公開対象主な確認場所
Deploy from a branch指定ブランチのルートまたは/docsSettings → Pages
GitHub Actionsワークフローがアップロードした成果物Actionsの実行ログとartifact

独自のビルド処理を使う場合はGitHub Actionsが適している。完成済みの静的ファイルをそのまま公開するだけなら、ブランチからの公開で構成を単純にできる。

05 / BUILD

ビルドとデプロイを分けて考える

ビルドはソースから公開用ファイルを作る処理であり、デプロイは完成したファイルを公開環境へ配置する処理である。HTMLを直接管理するサイトでは変換処理が少ないが、静的サイトジェネレーターやCMSを使う場合はビルド工程が必要になる。

JekyllはMarkdownやHTMLから静的サイトを生成する仕組みで、GitHub Pagesに組み込まれている。Jekyll以外のジェネレーターや独自処理を使う場合は、GitHub Actionsでビルドして成果物を渡す構成にできる。

MARK BENCH

microCMSから記事を取得して静的HTMLを作る工程がBUILD、生成したdist/をGitHub Pagesへ配置する工程がDEPLOYである。

06 / URL

URLとドメインの用語を整理する

既定ドメインはgithub.ioを使うURLである。独自ドメインは所有するドメインをPagesへ割り当てる構成であり、サブドメインとapexドメインではDNS設定が異なる。

  1. 既定URLで正しく公開できることを先に確認する。
  2. サイト種別とベースパスを確認する。
  3. 独自ドメインを使う場合はドメインを検証する。
  4. GitHub側のCustom domainとDNSレコードを対応させる。
  5. HTTPSの適用状態を確認する。

用語を個別に暗記するより、ファイルがリポジトリから公開URLへ届くまでのどこを指しているかで整理すると、設定変更の影響を判断しやすくなる。
