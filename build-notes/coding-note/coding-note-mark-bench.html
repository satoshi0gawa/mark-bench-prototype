01 / OVERVIEW

制作概要

MARK BENCHは、Web制作で繰り返し使う小さなツール、再利用可能なUIパーツ、制作・運用の記録を一か所へ集約するための静的サイトです。機能を使う場所、コードを参照する場所、実装の判断を残す場所を同じサイト内に整理しています。

ブラウザで動く機能はHTML、CSS、Vanilla JavaScriptで実装し、記事取得やHTML生成などの公開前処理はNode.jsへ分離しました。生成した静的ファイルはGitHub Actionsを経由してGitHub Pagesへ公開します。

MARK BENCHの制作概要
項目 内容
制作種別 Web制作支援ツール・UIリファレンス・制作記録サイト
対象 Web制作時に機能、実装例、作業記録を参照したい制作者
主要コンテンツ TOOLS / WEB PARTS / BUILD NOTES / ABOUT
公開方式 静的ビルド / GitHub Actions / GitHub Pages
PROJECT SUMMARY

「使う」「見る」「記録する」を一つの構造へまとめ、追加する機能や記事の管理元が判断しやすいサイトを目指しました。

02 / REQUIREMENTS

目的と要件

制作の起点は、Web制作中に別々の場所へ散らばりやすい変換ツール、UI実装例、技術メモを、共通の操作と見た目で参照できるようにすることでした。

  1. ツールへの入力内容を原則としてブラウザ内だけで処理する。
  2. UIパターンを動作例と実装コードの両方から確認できるようにする。
  3. サイト単位の実装記録とテーマ単位の学習記録を分けて蓄積する。
  4. 320pxからPCまで、主要情報と操作を維持する。
  5. キーボード操作、フォーカス表示、動きを抑える設定へ対応する。
  6. 検証と静的生成を自動化し、公開物へ認証情報を含めない。
CORE REQUIREMENT

機能を増やしても、利用者が「どこで使うか」、制作者が「どこを直すか」を判断できる構造を保ちます。

04 / STRUCTURE

サイト構成とコンテンツ管理

主要コンテンツをTOOLS、WEB PARTS、BUILD NOTES、ABOUTへ分けています。BUILD NOTESの中でも、サイト単位のCODING NOTEとテーマ単位のNOTE to SELFを分離し、記録の粒度を揃えました。

コンテンツの役割と管理方法
コンテンツ 役割 管理方法
TOOLS ブラウザで使うWeb制作ユーティリティ Git上のHTML・JavaScript
WEB PARTS UIの動作例と実装コード Git上のHTML・CSS・JavaScript
CODING NOTE 1サイトごとの設計・実装記録 Git上の個別静的HTML
NOTE to SELF 学習内容と制作上の気づき microCMSから静的生成
ABOUT サイトの目的と実装方針 Git上の静的HTML

microCMSの管理対象をNOTE to SELFへ限定し、生成物のdist/は直接編集しません。CODING NOTEは完成した制作物の入口ではなく、仕様と実装判断を詳しく残す役割を持たせます。

CONTENT RULE

制作物の概要はポートフォリオ、詳しい設計・実装はCODING NOTE、テーマ単位の学習記録はNOTE to SELFへ分けます。

05 / ARCHITECTURE

技術構成とファイル設計

共通値、共通コンポーネント、ページ固有レイアウト、機能別スクリプトを分け、変更の影響範囲を追いやすくしています。色、フォント、余白、コンテンツ幅はCSSカスタムプロパティへまとめました。

  --page-gutter: clamp(1rem, 3vw, 3rem);
  --content-width: 1440px;
  --site-frame-width: min(70%, var(--content-width));
  --site-rail-width: calc((100% - var(--site-frame-width)) / 2);
}

06 / IMPLEMENTATION

主要な実装ポイント

コンテンツごとに利用目的は異なりますが、検索・絞り込み、状態表示、コード参照、静的生成を共通の設計方針で組み立てています。

主要コンテンツの実装ポイント
対象 実装内容 設計上のポイント
TOOLS 入力、変換、生成、検索、カテゴリー絞り込み、並び替え 入力内容を原則ブラウザ内で処理し、選択状態をaria-pressedへ同期
WEB PARTS 動作例、パターン絞り込み、HTML・CSS・JavaScriptのコピー c-接頭辞とBEMで掲載コードを統一し、コード領域内だけをスクロール
NOTE to SELF microCMS取得、データ検証、本文サニタイズ、一覧・詳細生成 参照リンクや関連CTAをデータがある場合だけ出力
共通UI パンくず、主要ナビゲーション、表示演出、現在年の更新 JavaScriptが無効でも主要情報を読めるHTMLを基礎にする

TOOLS一覧はカードのdata-name、data-search、data-categoryから検索条件を判定し、URLのcategoryとqから初期状態を復元します。

NOTE to SELFでは、記事セクションの配列順から目次と番号を生成します。CMS本文は許可した要素・属性へサニタイズし、ページ構造を担うh1・h2を本文内で使用できないよう検証しています。

SECURITY

microCMSの認証情報はビルド環境だけで使用し、公開HTMLやブラウザ側のJavaScriptへ含めません。

07 / QUALITY

レスポンシブとアクセシビリティ

PCでは左側にパンくず、中央にメインコンテンツ、右側に主要ナビゲーションを配置します。1024px以下ではパンくずとナビゲーションを上部へ移し、メインコンテンツを全幅へ広げます。

画面幅ごとのレイアウト切り替え
条件 表示の切り替え
1025px以上 左右のレールと中央コンテンツ
1024px以下 上部パンくず、横並びナビゲーション、全幅のメインエリア
640px以下 余白、見出し、カード、操作領域を小さい画面向けに調整
WEB PARTSの1280px以上 パターン一覧を基本2列で表示
  1. 本文へ移動するスキップリンクを全ページへ用意します。
  2. 主要操作をキーボードだけで完了できる状態にします。
  3. :focus-visibleによるフォーカス表示を維持します。
  4. 状態は色だけに依存せず、テキストやARIA属性にも反映します。
  5. prefers-reduced-motionでは不要な動きを省略します。
  6. 表とコードは要素内でスクロールさせ、ページ全体の横スクロールを防ぎます。

最小表示幅は320pxです。Intersection Observerを利用できない環境では演出を省略し、コンテンツ自体は表示された状態を保ちます。

08 / CHALLENGES

課題と解決

静的ページ、ブラウザ内ツール、CMS記事を一つの公開成果物へまとめるため、管理元と実行環境の違いを吸収する必要がありました。

制作上の課題と解決方法
課題 原因 解決
静的HTMLとCMS記事を同じサイトへ配置する GitとmicroCMSで管理元が異なる ビルド時に静的ファイルをコピーし、NOTE to SELFだけを生成して統合
機能の異なるツールへ一貫したUIを提供する 入力形式と出力形式がツールごとに異なる 操作領域、状態表示、コピー処理、ドキュメント構造を共通化
小さい画面で表とコードがレイアウトを押し広げる 内容に固有の最小幅が必要 ページではなく表・コード領域だけにスクロールを限定
GitHub Pagesのサブパスで参照切れが起きる ルート絶対パスがリポジトリ配下URLと一致しない 相対パスを維持し、ビルド前後のローカル参照を自動検証
RESULT

管理元の違いをビルド工程で吸収し、公開後はすべてのコンテンツを同じ静的サイトとして配信できる構成にしました。

09 / REVIEW & DELIVERY

検証と公開

HTML構造、ローカル参照、SEO、ツール処理、CMS記事、秘密情報を自動検証します。表示と操作は自動検証だけに頼らず、主要な画面幅とキーボード操作でも確認します。

  1. mainとh1の数、IDの重複、スキップリンクを確認します。
  2. ローカル参照とページ内アンカーのリンク先を確認します。
  3. title、description、canonical、OGP、構造化データを確認します。
  4. TOOLSの入力、出力、コピー、リセット処理を確認します。
  5. CMS記事データとリッチテキストのサニタイズを確認します。
  6. 生成物へ認証情報が混入していないか確認します。
npm run sync:head
npm run check
npm run check:detail
npm run build
